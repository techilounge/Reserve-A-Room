**Checkpoint:** 2026-10-27. Phase 0 architecture for owner review; no calendar schema or feature has been implemented. Do not begin Phase 1 until the owner explicitly approves continuation. The full requirements and review gates are in the owner's Church Calendar master prompt. This document is a design proposal, not a record of deployed behavior.

**Baseline:** GitHub `main` was checked read-only and resolves to `1f287eecb0979f40339011a49ab3b99508ec6514`, matching local `origin/main` at review. `codex/church-calendar-management` was created at that commit. ## 1. Existing application and boundaries

- `reservations` is the operational room hold, with `[start_at,end_at)` GiST exclusion for `pending` and `approved` records. The trigger `private.validate_reservation` enforces room active/reservable state, lead time, horizon, a single local day, daily bookable hours, grid alignment, and policy snapshots. `private.enforce_status_transition` validates lifecycle. Several required fields include requester identity, E.164 phone, ministry selection and a guest-token seed/hash. Calendar-created rows need explicit, verified field mappings and must not accidentally generate guest-manageable links or duplicate reservation emails.
- `reservation_series` stores staff recurrence, while `src/lib/recurrence/dates.ts` generates local dates and `src/lib/datetime` converts wall times to instants. Existing expansion hard-codes **12 months and 50 instances**, so do not increase its constants globally. Extract a bounded generic candidate generator with explicit limits; preserve the existing reservation wrapper and regression tests unchanged.
- Guest recurring requests are a separate `recurring_reservation_requests` submission and staff review flow, not materialized room bookings. Reuse its form conventions, consent/abuse controls, notification and outbox patterns, not its data model for planning.
- `/admin/calendar` and `getCalendar` display reservation entries by range with month/week/day and mobile agenda. Retain the URL; relabel it **Room Schedule** in the appropriate later phase. The Church Calendar is a separate event read model at `/admin/church-calendar` with year/month/week/day/agenda and optional room-hold overlay.
- `permissions.ts`, `assertPermission`, `requireStaffPage`, RLS and `private.require_staff` form the existing authorization model. New staff operations require a fresh active profile and independent SQL authorization. Planning-link users remain unauthenticated, scoped capabilities; no new permanent role.
- `notifications` has recipient ownership, read state and separate reservation / recurring-request foreign keys. Preserve those columns and existing RPC contracts; add nullable typed calendar plan/event references with exactly-one-target validation as needed and version the RPC/read model. Do not replace live data with polymorphic IDs in the first release. A later migration may generalize once dual-read/backfill and referential integrity are demonstrated.
- `email_logs` is reservation-specific. `system_email_logs` has an entity ID, event type, payload and uniqueness on `(event_type, entity_type, entity_id, recipient)`. Reuse branded React Email, transactional enqueue and service-role workers, extending uniqueness with a durable **event/revision/reminder occurrence key**: the existing constraint alone would suppress legitimate repeated invitations, revisions and deadline reminders. Never perform the external send in the approval transaction.
- `audit_logs` already stores actor, action, entity and metadata. Add calendar action formatting and sanitized metadata; never record tokens, private URLs or secrets. Existing responsive shell, mobile More sheet, confirmation dialog, CSV/PDF and legal/privacy components are reusable.
- Deployed baseline has a daily combined cron; the local remediation separates bounded email and recurrence workers. Calendar work must first verify which version ships. Reuse protected jobs and leases; add one bounded calendar-job dispatcher for reminder generation and eventual sync, with idempotent logical job keys, backoff and observable failures. Vercel Hobby schedules daily with hourly precision, so deadline reminders are approximate and cannot promise minute-exact delivery.

## 2. Proposed data contract

All IDs are UUIDs unless noted. All new tables have `created_at`, `updated_at` where mutable, RLS enabled, explicit grants, restrictive FKs and bounded text; audit history and finalized/cancelled records are retained. Enums can be checked text to allow append-only evolution. No SQL below is an applied migration.

## 3. State machines and ownership

Only narrowly granted RPCs transition state; direct browser table writes are denied.

- **Cycle:** `draft → open → review → finalized → archived`; authorized Super Admin can explicitly reopen `review/finalized → open` with a reason/audit. Archived requires explicit unarchive to a safe state. Closed/finalized/archived cycles reject planning mutations regardless of cookie validity; resubmission requires an explicit reopen.
- **Plan:** `draft → submitted → under_review`; event decisions derive `changes_requested`, `partially_approved`, or `approved`; close produces `closed`. One private recalculation function owns derived status, locking plan and considering all non-deleted events. A deliberate reopen increments a revision and records who/why. Empty plan submission needs an explicit confirmation.
- **Event:** `draft → submitted → under_review → changes_requested → submitted`; review may also transition to `approved` or `declined`; `approved → cancelled`. Declined/cancelled are historical, not editable by the ministry. Approved edits use a separate reviewed transactional RPC and increment revision. Draft deletion is limited to never-submitted drafts and records an audit tombstone.
- **Occurrence:** `scheduled → cancelled` through the calendar RPC; individual cancellation preserves parent and historical rows. Reviving a cancelled instance requires a new reviewed operation, not an unchecked update.
- **Room/resource request:** `requested → allocated → released`; reallocation is a fresh locked approval/update, never an unrestricted row edit. Existing linked reservation states stay governed by their own transition trigger.

Submission, review, approval, edit and cancellation must lock in a consistent order: cycle/plan, event, occurrences sorted by ID, rooms sorted by ID, resources sorted by ID. Make the cycle/event check and data mutation one transaction to prevent a close/revoke racing an edit. Ministry service RPCs must verify the grant hash/version/expiry/revocation, plan/cycle relationship and requested event ownership inside the same transaction on **every** read or mutation; never trust IDs or role assertions in the browser.

## 4. Scheduling, conflicts and atomic approval

Calendar generation supports one-time, multi-day, explicit dates and the current recurrence rule variants. A 3-year cycle and **1,200 occurrences per event** accommodate daily schedules while bounding mistakes; reject overflow instead of silently truncating. Validate end boundaries inclusively, skipped invalid dates and duplicate nth-weekday dates. Compute each start/end from its local date and stored IANA timezone using existing datetime helpers; reject nonexistent DST wall times, and document the choice for ambiguous fall-back times before implementation. Event ranges describe public times; occupancy includes setup/cleanup. Tests cover both DST transitions and offsets across them.

Hard blocks: pending/approved room overlap for `[occupancy_start,occupancy_end)`; insufficient concurrently allocated resource quantity; inactive/nonreservable room or inactive resource; planned food in a prohibiting room; invalid schedule; and an explicitly **exclusive** approved event overlapping another covered event. A church-wide scope by itself is not exclusive. Soft warnings: same-ministry overlap, two church-wide events, configurable large-event overlap/shared audience, and attendance above room capacity. Warnings require a reason tied to the current conflict fingerprint; stale overrides cannot authorize changed data. Define audience/large-event thresholds and the exact scope of exclusivity with the owner before building Phase 5.

`approve_calendar_event(event_id, expected_revision, decisions)` is an authenticated SECURITY DEFINER RPC with empty search path, fully qualified names and `private.require_staff()`. It locks and rechecks current revision, state, occurrences, policy and conflicts; locks requested rooms/resources in stable order; creates all approved room holds, allocations, audit/notification rows and email outbox rows; sets event approval and recalculates plan; and commits atomically. Any failed insert, exclusion violation, quantity shortage or stale decision rolls back the entire event including earlier holds. Two competing room approvals are settled by the existing exclusion constraint. For quantities, serialize *all* allocation, release, approved-edit and resource-quantity changes on each resource row; after locking, recompute concurrent demand using an endpoint sweep across overlapping `[)` ranges (not a naive sum of all individually overlapping bookings, which can overcount disjoint periods). A subsequent transaction sees the committed allocations. Use real parallel PostgreSQL connections for race tests; PGlite alone may not prove concurrency.

The existing trigger enforces more than the horizon: no overnight holds, grid alignment and bookable hours. A calendar exception must be explicit and narrow. Proposal: allow beyond-horizon and occupancy outside the ordinary grid/day window only for holds created/updated inside the authorized calendar transaction after occurrence/room linkage and active/reservable/food checks; do **not** bypass overlap, past-time, resource or authorization checks. Split multi-day occupancy at local-day boundaries if existing operational displays require one-day rows; decide whether to allow overnight occupancy or preserve overnight gaps with the owner before Phase 6. Record exception reasons and policy snapshots. Add an append-only trigger/function replacement that verifies a private, transaction-bound authorization capability created only by the approval RPC (for example an inaccessible private table keyed by transaction and event/occurrence, with cleanup). Never rely only on caller-controlled `source`, user-settable session variables, or UI. Revoke direct insert/update/delete and audit every reachable existing RPC so none can forge the capability. Ordinary guest and staff RPCs retain current validation and limits.

For calendar-managed rows, database guards reject ordinary edit/reschedule/cancel/retry paths unless the same transaction-bound calendar capability exists. Calendar event cancellation or occurrence cancellation atomically cancels future linked holds, releases resources, invalidates feed/sync cache and queues notices; retain past rows. Existing email triggers need source-aware handling to avoid guest-management emails and duplicate staff alerts. Tests must include manipulated source/IDs, staff role, RLS, direct mutation, ordinary horizon rejection, long-range approved event, multi-room rollback and simultaneous approvals.

## 5. Invitation security, notifications and publishing

Generate a random seed, derive an HMAC token with a dedicated `CALENDAR_PLAN_LINK_SECRET` and domain separation, and store only seed plus token hash. The emailed URL contains a plan reference and token. A non-consuming GET confirmation page prevents mail scanners from spending an invite; a user-initiated POST verifies the grant and exchanges it for a Secure, HttpOnly, SameSite=Lax cookie scoped to `/calendar-plan/<reference>`, then redirects to a clean URL with `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Prefer a separate random session credential/hash tied to the current grant and expiry; rotation/revocation invalidates all sessions. A cookie alone is not authorization: each server action/RPC revalidates scope, grant version, cycle and event ownership. Guard CSRF using same-origin Server Actions plus explicit Origin checks for custom POSTs; rate-limit exchange by HMACed IP/reference. No token in logs, analytics, public feeds, markup after exchange, or third-party requests.

Queue branded invitation, reminder, submission, revision, approval, decline, cancellation and staff notices inside the relevant DB transaction. Delivery is separate and failure cannot roll back business changes. Version each semantic notification so resend and repeated edits are legitimate yet retries stay idempotent. Current Resend deduplication lasts 24 hours and requires the same payload; the local remediation fingerprints each provider payload and parks changed or late retries for review, but it must be deployed and verified before calendar work relies on it.

Public `/calendar` and versioned `/api/calendar/public.json` and `/api/calendar/public.ics` use a dedicated allowlisted SQL view/RPC selecting **approved + public + scheduled** occurrences only. Never return `select *`; omit planning contacts, internal descriptions/notes, resource notes, conflicts, tokens and cancelled/pending/declined/internal events. Stable ICS UIDs derive from occurrence UUID, escaped/folded RFC 5545 fields, UTC timed events with timezone-aware inputs and correct all-day exclusive end dates. Use `LAST-MODIFIED`, ETags and bounded range/pagination for JSON; explicitly invalidate caches after approval/edit/cancellation. Never publish a virtual private meeting URL without explicit public designation. Test feed content, cancellation, escaping, recurrence and cache invalidation.

## 6. Stonehill website discovery and integration decision

Public search results show Stonehill has both an [Events page](https://stonehillchurch.org/our-events/) and a separate [Tribe Events calendar](https://stonehillchurch.org/events/?tribe_redirected=1) with recurring series links. This is evidence consistent with The Events Calendar, but it does **not** establish which calendar is authoritative, installed plugin versions/Pro entitlement, whether the homepage uses a separate embedded source, or API/credential permissions. Direct read-only requests to `/wp-json/` and `/wp-json/tribe/events/v1/` were inaccessible from the research tool, so availability and write support are **unverified**, not assumed absent. The vendor's [REST documentation](https://docs.theeventscalendar.com/rest-endpoints/) describes possible event endpoints, but actual site behavior must be confirmed by its owner in a staging environment.

Recommended staged integration: retain the website's current manual calendar during planning; owner inventories plugin, API, recurrence and upstream calendar sources, timezone, site firewall, permissions and Application Password availability. Prototype read-only discovery and a dry-run mapping; reconcile/import future events with preview and no automatic room/ministry guesses. After owner approval only, use a dedicated least-privilege server-only account over HTTPS, a durable one-way sync queue and stable external IDs per actual target occurrence. Create/update/unpublish only approved public data; make retries idempotent and notify staff on failure without blocking approval. Validate recurrence and DST on the actual plugin version. No live WordPress sync or writes are authorized by Phase 0.

## 7. Phase-by-phase execution and gates

1. **Cycles and invitations:** append migration for cycles/plans/grants, least-privilege RPCs, Super Admin UI, branded invitation, revoke/resend, audit and unit/DB/browser tests. Test token rotation, expiry, isolation and closed-cycle race.
2. **Planning portal and submission:** safe token exchange and scoped session; draft CRUD/duplication; typed one-time/multi-day/multiple-date/recurring schedules; requested rooms/resources; submission/revision; staff list. Test ID tampering, complete flow and mobile. **Stop for owner review.**
3. **Occurrence engine:** extract generic bounded local-date primitives while retaining existing 12-month/50 reservation wrapper; materialize up to 1,200 cycle-bound instances, DST, setup/cleanup; rerun all existing recurrence tests.
4. **Resources:** catalog, quantities and occurrence requests; locking and quantity-change invariants; DB concurrency tests.
5. **Conflicts:** unified DB-authoritative hard checks, revision-bound soft overrides and conflict center; tests for overlapping ranges and invalidation.
6. **Approval:** append reservation linkage/guards and carefully isolated horizon/occupancy exception; atomic approval, edit, cancellation, notices and audit. Test two concurrent approvals, resource races, all-or-nothing three-room failure, unauthorized bypass and all existing reservation flows. **Stop for owner functional review.**
7. **Master calendar:** Church Calendar and filters/layers; relabel existing `/admin/calendar` Room Schedule; year view/mobile agenda and accessible keyboard controls.
8. **Planning dashboard/automation:** progress, conflict metrics, reminder jobs, copy prior plans as drafts with explicit date review and idempotency.
9. **Public calendar and feeds:** allowlisted approved/public scheduled data, ICS/JSON, privacy/cache tests and accessible mobile pages.
10. **WordPress foundation:** only after discovery, staging fixtures, mapping, durable outbox, bounded retries and dry run. **Stop before live automatic publishing and obtain owner approval.**
11. **Migration/reconciliation:** after owner approval, preview future-event import, preserve external IDs, resolve duplicates and obtain review before any official overwrite.
12. **Reporting/hardening:** reusable exports, role/RLS/grant/security audit, real concurrent DB tests, accessibility, performance, PWA and full regression. Each phase runs typecheck, lint, unit, DB and build; relevant browser checks run after the build. Full suite before release.
