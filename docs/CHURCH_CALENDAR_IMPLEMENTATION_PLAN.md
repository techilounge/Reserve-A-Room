## 1. Existing application and boundaries

- `reservations` is the operational room hold, with `[start_at,end_at)` GiST exclusion for `pending` and `approved` records. The trigger `private.validate_reservation` enforces room active/reservable state, lead time, horizon, a single local day, daily bookable hours, grid alignment, and policy snapshots. `private.enforce_status_transition` validates lifecycle. Several required fields include requester identity, E.164 phone, ministry selection and a guest-token seed/hash. Calendar-created rows need explicit, verified field mappings and must not accidentally generate guest-manageable links or duplicate reservation emails.
- `reservation_series` stores staff recurrence, while `src/lib/recurrence/dates.ts` generates local dates and `src/lib/datetime` converts wall times to instants. Existing expansion hard-codes **12 months and 50 instances**, so do not increase its constants globally. Extract a bounded generic candidate generator with explicit limits; preserve the existing reservation wrapper and regression tests unchanged.
- Guest recurring requests are a separate `recurring_reservation_requests` submission and staff review flow, not materialized room bookings. Reuse its form conventions, consent/abuse controls, notification and outbox patterns, not its data model for planning.
- `/admin/calendar` and `getCalendar` display reservation entries by range with month/week/day and mobile agenda. Retain the URL; relabel it **Room Schedule** in the appropriate later phase. The Church Calendar is a separate event read model at `/admin/church-calendar` with year/month/week/day/agenda and optional room-hold overlay.
- `permissions.ts`, `assertPermission`, `requireStaffPage`, RLS and `private.require_staff` form the existing authorization model. New staff operations require a fresh active profile and independent SQL authorization. Planning-link users remain unauthenticated, scoped capabilities; no new permanent role.
- `notifications` has recipient ownership, read state and separate reservation / recurring-request foreign keys. Preserve those columns and existing RPC contracts; add nullable typed calendar plan/event references with exactly-one-target validation as needed and version the RPC/read model. Do not replace live data with polymorphic IDs in the first release. A later migration may generalize once dual-read/backfill and referential integrity are demonstrated.
- `email_logs` is reservation-specific. `system_email_logs` has an entity ID, event type, payload and uniqueness on `(event_type, entity_type, entity_id, recipient)`. Reuse branded React Email, transactional enqueue and service-role workers, extending uniqueness with a durable **event/revision/reminder occurrence key**: the existing constraint alone would suppress legitimate repeated invitations, revisions and deadline reminders. Never perform the external send in the approval transaction.
- `audit_logs` already stores actor, action, entity and metadata. Add calendar action formatting and sanitized metadata; never record tokens, private URLs or secrets. Existing responsive shell, mobile More sheet, confirmation dialog, CSV/PDF and legal/privacy components are reusable.
- Deployed baseline has a daily combined cron; the local remediation separates bounded email and recurrence workers. Calendar work must first verify which version ships. Reuse protected jobs and leases; add one bounded calendar-job dispatcher for reminder generation and eventual sync, with idempotent logical job keys, backoff and observable failures. ## 2. Proposed data contract

All IDs are UUIDs unless noted. All new tables have `created_at`, `updated_at` where mutable, RLS enabled, explicit grants, restrictive FKs and bounded text; audit history and finalized/cancelled records are retained. Enums can be checked text to allow append-only evolution. No SQL below is an applied migration.

The ownership and allocation graph is:

```text
Calendar cycle
  └─ Ministry plan (owning ministry derived from the plan)
      ├─ Independent planning grants 0..N, each with its own sessions
      └─ Event
          ├─ Co-sponsoring ministries
          ├─ Schedule and specific dates
          ├─ Room templates and resource templates (event-wide defaults)
          └─ Occurrences (stable logical identities)
              ├─ Occurrence room requests → approved reservations
              └─ Occurrence resource requests → confirmed allocations
```

## 3. State machines and ownership

Only narrowly granted RPCs transition state; direct browser table writes are denied.

- **Cycle:** `draft → open → review → finalized → archived`; authorized Super Admin can explicitly reopen `review/finalized → open` with a reason/audit. Archived requires explicit unarchive to a safe state. Closed/finalized/archived cycles reject planning mutations regardless of cookie validity; resubmission requires an explicit reopen.
- **Plan:** `draft → submitted → under_review`; event decisions derive `changes_requested`, `partially_approved`, or `approved`; close produces `closed`. One private recalculation function owns derived status, locking plan and considering all non-deleted events. A deliberate reopen increments a revision and records who/why. Empty plan submission needs an explicit confirmation.
- **Event:** `draft → submitted → under_review → changes_requested → submitted`; an authorized reviewer may decline from `submitted`, `under_review` or `changes_requested`, or approve from `submitted` / `under_review` after all checks. `approved → cancelled`. Declined/cancelled are historical, not editable by the ministry. Approved edits use a separate reviewed transactional RPC and increment revision. Draft deletion is limited to never-submitted drafts and records an audit tombstone.
- **Occurrence:** `scheduled → cancelled` for a user cancellation or `scheduled → superseded` for a materially replaced schedule through a reviewed calendar RPC; both preserve parent, row identity and history. Reviving a cancelled instance requires a new reviewed operation, not an unchecked update. Future regeneration creates linked replacement rows for genuinely new instances; past rows are immutable.
- **Room/resource request:** `requested → allocated → released`; reallocation is a fresh locked approval/update, never an unrestricted row edit. Existing linked reservation states stay governed by their own transition trigger.

Submission, review, approval, edit and cancellation must lock in a consistent order: cycle/plan, event, occurrences sorted by ID, rooms sorted by ID, resources sorted by ID. Make the cycle/event check and data mutation one transaction to prevent a close/revoke racing an edit. Ministry service RPCs must verify the grant hash/version/expiry/revocation, plan/cycle relationship and requested event ownership inside the same transaction on **every** read or mutation; never trust IDs or role assertions in the browser.

**Template expansion and exceptions:** Phase 2 persists any number of event-wide room and resource templates independently of occurrence rows. Phase 3 generates each occurrence's effective requests idempotently, using unique occurrence/resource and occurrence/room keys. For each occurrence, apply defaults, then explicit exception tombstones/removals, quantity overrides, and additions in that order. A room replacement is a removal plus an addition; additional resources and one-off room additions are separate exception rows. Template edits increment a revision and transactionally recompute only eligible future/unapproved requests while retaining explicit exceptions; they must never silently overwrite per-occurrence overrides. Approved changes require the Phase 6 transactional reapproval/edit path and release/revalidate old allocations. Concurrent generation and editing lock the event/revision and reject stale revisions. A 52-week meeting needs one Conference Room selection, while VBS may select multiple default rooms once.

## 4. Scheduling, conflicts and atomic approval

Calendar generation supports one-time, multi-day, explicit dates and the current recurrence rule variants. A 3-year cycle and **1,200 occurrences per event** accommodate daily schedules while bounding mistakes; reject overflow instead of silently truncating. Validate end boundaries inclusively, skipped invalid dates and duplicate nth-weekday dates. Compute each start/end from its local date and stored IANA timezone using existing datetime helpers; reject nonexistent DST wall times, and document the choice for ambiguous fall-back times before implementation. Event ranges describe public times; occupancy includes setup/cleanup. Tests cover both DST transitions and offsets across them.

### Operational conflicts, planning conflicts, and warnings

An **operational conflict** compares an event with a pending/approved ordinary reservation, an approved calendar-created reservation, or a confirmed resource allocation. It is a hard block when actual room/resource capacity is unavailable. Exclude the event's own linked reservation/allocation on an authorized approved-event edit and count an approved calendar hold only once; the existing reservation GiST exclusion remains final authority for the room.

A **planning conflict** compares active proposed event occurrences and their effective room/resource requests before any operational holds exist. A draft produces no cross-ministry conflict; `submitted` and `under_review` participate. `changes_requested` continues to participate using the **last submitted snapshot**, not an in-progress private revision, until resubmitted, declined or its plan is closed; this is an explicit recommendation so intent does not vanish during review. `approved` participates as an operational commitment, not a second provisional request. `declined`, `cancelled`, superseded/cancelled occurrences and proposals in closed plans are excluded. On resubmission atomically replace the visible snapshot and invalidate stale conflict decisions; staff can compare drafts privately for the owning plan without exposing another ministry's details.

The staff Conflict Center labels hard operational/policy blocks, unresolved planning conflicts and soft calendar warnings distinctly; it shows affected occurrence, date, resource/room, safe staff-only context and actions. Ministry users see only their own conflicts with non-identifying availability guidance. A planning conflict is a prominent **decision required**, not an automatic physical hard block: staff must explicitly select an event to advance and record the resolution/priority, or revise/withdraw requests. Approval of the selected proposal may proceed if actual operational checks pass; the competing proposal remains submitted and is re-evaluated immediately, becoming operationally blocked if the winner takes the room/resource. No decision can override an existing hard conflict, silently decline another event, or claim confirmed resources for an unapproved event. Resolved planning decisions are fingerprinted against both submitted revisions and affected occurrence/resource ranges; any material change invalidates them. Simultaneous conflicting decisions are serialized or rechecked in the approval transaction.

| Proposed occurrence versus | Result before approval | Approval treatment |
| --- | --- | --- |
| Other active proposal, same room and overlapping occupancy | Room planning conflict | Staff decision/priority or change required; no operational hold yet. |
| Existing pending/approved ordinary reservation | Hard operational room conflict | Blocks until released or schedule/room changes. |
| Approved calendar event's linked active room reservation | Hard operational room conflict | Blocks; do not double-count its occurrence and reservation. |
| Other active proposal(s) for same resource | Provisional resource planning conflict when combined concurrent demand exceeds capacity | Staff decision/priority or change required; no confirmed allocation yet. |
| Confirmed allocation(s) | Hard operational resource conflict if confirmed demand plus this request exceeds capacity at any instant | Blocks until capacity/request/time changes. |
| Proposed exclusive event or proposal requesting exclusivity | Planning conflict if the approved exclusivity policy says they overlap | Decision required; exact coverage remains an owner decision before Phase 5. |
| Approved exclusive event or an exclusive candidate versus an approved event | Hard block if the approved exclusivity policy covers the pair | Blocks; never assume all offsite, public, or church-wide events are covered without policy. |
| Same-ministry event | Soft warning | Record a reason tied to the current fingerprint if proceeding. |
| Church-wide event overlapping another church-wide event | Soft warning, unless explicitly exclusive and covered by policy | Record a reason, or block when an approved exclusive applies. |
| Large attendance/shared audience | Soft warning once owner-approved threshold/audience criteria exist | Record a reason. |
| Attendance above room capacity | Soft warning | Record a reason; existing capacity philosophy remains. |
| Food planned in a prohibiting room; inactive/nonreservable room; inactive resource; invalid schedule | Hard policy block | Correct the request or obtain a separately authorized policy change; no ordinary override. |

For quantities, calculate **confirmed capacity** and **provisional demand** separately. Sweep sorted occupancy endpoints for each resource using `[start,end)` semantics (process end before start at the same instant): confirmed allocations form baseline demand; add the effective requested quantities of participating proposals for planning warnings. Flag intervals where the combined concurrent sum exceeds `available_quantity`; do not sum disjoint intervals that merely each overlap a long candidate. On approval ignore other provisional demands for the hard physical check, but require their planning decisions, lock resource rows in stable order, recompute confirmed demand plus the candidate, and allocate only if capacity remains. Two candidate approvals racing for one van must yield exactly one allocation; planning warnings never reserve capacity.

`scope` answers what kind of activity an event is (`ministry`, `church_wide`, `administrative`, `community`); `protection` is only `normal` or `exclusive`. Church-wide does not imply exclusivity. The provisional exclusive rule is a hard block against another approved, covered Church Calendar event with overlapping **owner-selected event or occupancy range**. Whether coverage means all events, on-site only, entire property, particular scopes or another policy is explicitly undecided; do not hard-code it before owner decision in Phase 5. Proposed-versus-proposed exclusive overlaps remain planning decisions until a winner is approved. Overrides for soft/planning decisions include conflict type, normalized identities and both revision fingerprints; they cannot override hard conflicts.

`approve_calendar_event(event_id, expected_revision, decisions)` is an authenticated SECURITY DEFINER RPC with empty search path, fully qualified names and `private.require_staff()`. It locks and rechecks current revision, state, occurrences, policy and conflicts; locks requested rooms/resources in stable order; creates all approved room holds, allocations, audit/notification rows and email outbox rows; sets event approval and recalculates plan; and commits atomically. Any failed insert, exclusion violation, quantity shortage or stale decision rolls back the entire event including earlier holds. Two competing room approvals are settled by the existing exclusion constraint. For quantities, serialize *all* allocation, release, approved-edit and resource-quantity changes on each resource row; after locking, recompute concurrent demand using an endpoint sweep across overlapping `[)` ranges (not a naive sum of all individually overlapping bookings, which can overcount disjoint periods). A subsequent transaction sees the committed allocations. Use real parallel PostgreSQL connections for race tests; PGlite alone may not prove concurrency.

The existing trigger enforces more than the horizon: no overnight holds, grid alignment and bookable hours. A calendar exception must be explicit and narrow, with independent audited capabilities:

- `bypass_advance_horizon`: recommended automatic exception only within a verified calendar approval transaction, subject to cycle and future-time validation.
- `allow_outside_public_booking_hours`, `allow_non_grid_times`, `allow_overnight_occupancy`: independently **disabled by default**; owner must decide whether and how each can be authorized before Phase 6. An approval does not automatically grant them. Distinguish public booking hours from actual building access hours before adopting an exception.
- Never automatically bypass room overlaps, inactive rooms, food prohibitions, authorization, resource availability or past-time checks. A nonreservable room stays blocked unless a separately approved, audited policy explicitly authorizes it; do not infer that authority from calendar status.

If overnight occupancy is approved, define continuous occupancy and any split-at-local-midnight representation without introducing release gaps or double-counting. Record which specific exception was exercised and policy snapshots. Add an append-only trigger/function replacement that verifies a private, transaction-bound authorization capability created only by the approval RPC (for example an inaccessible private table keyed by transaction and event/occurrence, with cleanup). Never rely only on caller-controlled `source`, user-settable session variables, or UI. Revoke direct insert/update/delete and audit every reachable existing RPC so none can forge the capability. Ordinary guest and staff RPCs retain current validation and limits.

For calendar-managed rows, database guards reject ordinary edit/reschedule/cancel/retry paths unless the same transaction-bound calendar capability exists. Calendar event cancellation or occurrence cancellation atomically cancels future linked holds, releases resources, invalidates feed/sync cache and queues notices; retain past rows. Existing email triggers need source-aware handling to avoid guest-management emails and duplicate staff alerts. Tests must include manipulated source/IDs, staff role, RLS, direct mutation, ordinary horizon rejection, long-range approved event, multi-room rollback and simultaneous approvals.

## 5. Invitation security, notifications and publishing

For each planner independently generate a random seed, derive an HMAC token with a dedicated `CALENDAR_PLAN_LINK_SECRET` and domain separation, and store only seed plus token hash. The emailed URL contains a plan reference and that planner's token. A non-consuming GET confirmation page prevents mail scanners from spending an invite; a user-initiated POST verifies the grant and exchanges it for a separate random session credential whose hash is stored against **that grant ID and version**, then sets a Secure, HttpOnly, SameSite=Lax cookie scoped to `/calendar-plan/<reference>` and redirects to a clean URL with `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Every access rechecks session hash/expiry/revocation, grant ID/version/expiry/revocation, owning plan/cycle state and event ownership; a cookie or plan ID alone grants nothing. Rotating or revoking Alice's grant invalidates only Alice's links/sessions, leaving Bob's valid. Reopening a closed plan does not automatically reinstate revoked grants. Independently invite, resend/rotate, revoke, expire, replace or restore each planner with an audited action, actor, grant ID and timestamp; never audit raw tokens, session secrets or private URLs. Guard CSRF using same-origin Server Actions plus explicit Origin checks for custom POSTs; rate-limit exchange by HMACed IP/reference. No token in logs, analytics, public feeds, markup after exchange, or third-party requests.

**Privacy and Terms gate before Phase 2 release:** draft proposed updates to `privacy.md` and `terms-of-service.md` describing planning contacts, event/public descriptions, internal notes, locations, virtual links, retention and relevant sharing, for **owner/legal review only**. Do not publish revised legal terms or assert legal requirements without approval. Recommend an accessible first-access screen for each grant presenting the approved policy/terms versions and recording the planner's affirmative acknowledgment with grant ID, versions and timestamp, subject to legal-team advice; compare this with the alternative administrative-invitation basis before implementation. Acceptance is per contact/version, not a shared plan-level flag; no unrelated consent should be bundled or silently inferred. Legal approval is a Phase 2 release gate, not a reason to delay completing this architecture.

Queue branded invitation, reminder, submission, revision, approval, decline, cancellation and staff notices inside the relevant DB transaction. Delivery is separate and failure cannot roll back business changes. Version each semantic notification so resend and repeated edits are legitimate yet retries stay idempotent. Current Resend deduplication lasts 24 hours and requires the same payload; the local remediation fingerprints each provider payload and parks changed or late retries for review, but it must be deployed and verified before calendar work relies on it.

Public `/calendar` and versioned `/api/calendar/public.json` and `/api/calendar/public.ics` use a dedicated allowlisted SQL view/RPC selecting **approved + public + scheduled** occurrences only. Never return `select *`; omit planning contacts, internal descriptions/notes, resource notes, conflicts, tokens and cancelled/pending/declined/internal events from normal listings. Never publish a virtual private meeting URL without explicit public designation.

**Stable public identity and regeneration:** assign each occurrence an immutable logical UUID independent of mutable schedule, time, room, resource, content and row revision. Derive a stable UID from `event_id + logical_occurrence_id` and a fixed domain, persist it when first published, and reuse it across an ordinary time/date/room/resource/description edit that is explicitly identified as the *same* logical occurrence. Update `LAST-MODIFIED` and revision/`SEQUENCE` for subscribers. An explicit-date entry maps to its stable entry identity; recurring expansion maps to existing logical IDs by stored provenance, not merely matching new dates. Do not automatically infer that a Wednesday occurrence is the same event as a Thursday occurrence when a recurrence rule is materially regenerated: a reviewed, deterministic mapping may preserve explicitly paired instances; otherwise mark affected **future** instances `superseded`, preserve their rows and old public IDs, and create new identities for replacements. Keep past occurrences and historical audit/allocations unchanged. An isolated cancellation similarly preserves its original ID and does not cancel other instances.

Normal public listings and JSON exclude cancelled/superseded instances. An ICS subscription may need a **minimal, previously public cancellation tombstone** with the prior UID, incremented sequence, `STATUS:CANCELLED` and no private data; whether to publish tombstones, retention duration and handling unpublish/public-to-internal transitions are explicit owner/privacy decisions before Phase 9. Removing items from a feed alone is not guaranteed to remove them from existing subscribers' calendars. Never expose details of an event that was not previously public or expose internal content in a tombstone; validate the chosen cancellation semantics with representative calendar clients. Use RFC 5545 escaping/line folding, UTC timed events with timezone-aware inputs, correct all-day exclusive end dates, bounded ranges/JSON pagination, ETags and explicit invalidation after approval/edit/cancellation. Tests must cover stable UIDs for ordinary edits, recurrence replacements, cancellation/tombstone behavior, privacy, DST, escaping and cache invalidation.

## 7. Phase-by-phase execution and gates

**Dependency choice: Option A.** Phase 1 supplies a small, real `calendar_resources` catalog with safe Super Admin setup/selection and independent grants; Phase 2 adds resource templates using that catalog. Full resource editing, availability and allocation arrive in Phase 4. This avoids asking ministries to select nonexistent resources and avoids prematurely implementing allocation/concurrency. Until Phase 4 the portal clearly labels resource selections as **requests, not allocations**; do not offer a fake availability or approval control. For Phase 2 UX review, schedule previews may be calculated transiently, but persistent occurrence records and conflict automation are not presented as complete before Phases 3–5.

1. **Cycles, invitations and minimum catalog:** append migrations for `calendar_cycles`, `ministry_calendar_plans`, `calendar_plan_access`, `calendar_plan_sessions` and minimal `calendar_resources` (`id/name/category/quantity/active` with Super Admin setup and staff/portal allowlisted read). Add least-privilege RPCs, independent invite/revoke/rotate, audit and branded emails. No event/occurrence/allocation tables yet. Test two grants to one plan, independent revocation/rotation/expiry, session isolation and closed-cycle races.
2. **Planning portal and submission:** append `calendar_events`, co-sponsor-only `calendar_event_ministries`, `calendar_event_schedules`, `calendar_schedule_dates`, `calendar_event_room_templates`, `calendar_event_resource_templates`, `calendar_event_submissions` and normalized submitted date/room/resource-template snapshots; add per-grant token exchange/session, draft CRUD/duplication, schedule inputs, multiple room/resource defaults, submission/revision and staff list. Test ID tampering, contacts, legal gate, template persistence, immutable submission revisions, mobile and non-allocating requests. **Stop for owner review.**
3. **Occurrence engine:** append `calendar_event_occurrences`, `calendar_event_room_requests`, `calendar_event_resource_requests`, `calendar_occurrence_room_exceptions`, `calendar_occurrence_resource_exceptions` and submission-scoped occurrence/room/resource request materializations; extract generic bounded local-date primitives while retaining the existing 12-month/50 reservation wrapper. 4. **Resources:** extend the early catalog with full Super Admin edit/deactivate and safe quantity changes; add resource allocation state/locking and availability primitives against occurrence requests. Add real concurrent database tests. No event approval is exposed until Phase 6.

6. **Approval:** append reservation source/linkage and database guards plus independently authorized policy exceptions; atomic approval, edit, cancellation, notices and audit. 12. **Reporting/hardening:** add necessary reporting indexes through append-only migration if measurements justify them; reusable exports, role/RLS/grant/security audit, real concurrent DB tests, accessibility, performance, PWA and full regression. ## 9. Open owner policy decisions

These are recommendations and phase-specific decisions, not newly approved policy. Independent planner grants and non-duplicated ministry ownership are architecture requirements; the **number** of planners is a separate policy choice.

1. **Cycle length:** owner approved a maximum of three years for Phase 1.
2. **Occurrences:** owner approved 1,200 per event as the architectural default for Phase 3.
3. **Exclusive scope and range:** whole property, all church events, on-site events only, specific scopes, and event versus occupancy range; decide before Phase 5. Church-wide alone is never automatically exclusive.
4. **Large-event warning:** attendance threshold and shared-audience criteria; decide before Phase 5.
5. **Overnight occupancy:** owner chose disabled by default; decide whether an authorized exception exists and how continuous holds work before Phase 6.
6. **Outside normal hours and non-grid times:** disabled by default; distinguish public booking hours from building access, and decide whether a separate override/actor/reason is required before Phase 6.
7. **Planner contacts:** owner approved independent primary, secondary and additional grants, up to five active planners per plan; revoked or expired grants do not count.
8. **Public cancellations:** remove from listings versus privacy-safe ICS cancellation tombstones, retention and public-to-internal behavior; decide before Phase 9.
9. **Cycle reopening:** owner approved Super Admin only with a required reason and audit.
10. **Planner Privacy/Terms:** owner approved the per-grant/per-version first-access acknowledgment design; obtain legal review and approval of draft terms before Phase 2 release.
11. **Website sources:** determine whether the public website calendars share a source and verify plugin/API permissions before Phase 10.
12. **Security workstream sequencing:** review its independent branch and preview/migration requirements before adopting it as a deployed calendar dependency; no production deploy is implied by this proposal.
